## Этап 1 · Гигиена репозитория (~полдня)

**Задачи**
- `git init`, `.gitignore`, baseline-коммит фазы 0 (доки, ADR, сид, макеты — до первой строки кода).
- Каркас Vite + React + TS (strict): `pnpm`, структура слоёв по [02-architecture.md](02-architecture.md):

```
src/app/        — роуты, провайдеры, корневой layout
src/features/   — экраны доменов: catches, map, places, weather, stats, auth
src/ui/         — переиспользуемые компоненты дизайн-системы (§6)
src/domain/     — типы (Catch, Place, SpeciesRef), чистая логика (валидация, агрегация)
src/data/       — repositories + Dexie (IndexedDB), outbox, sync engine
src/lib/        — supabase-клиент, map-provider, weather-абстракции
src/styles/     — tokens.css, base.css
```

- ESLint (typescript-eslint) + Prettier + stylelint; правило запрета литеральных HEX вне `tokens.css`.
- `pnpm verify` — одна команда: typecheck + lint + test + build. CI в будущем повторяет её без дублирования конфигурации.

**Результат:** пустое приложение собирается и проходит `pnpm verify`; история git начинается с документации.

**Проверка:** `pnpm verify` зелёный на чистой машине.

## Этап 2 · Токены и базовые компоненты (~3 дня)

**Задачи**
- `src/styles/tokens.css` — все токены [дизайн-системы §2–§4](06-design-system.md) как CSS-переменные `:root`, один в один, включая новые danger-токены.
- Inter self-host: woff2, субсет латиница+кириллица, `font-display: swap` (закрывает вопрос №4 §10 дизайн-системы).
- Компоненты §6: Button (4 варианта), Chip/фильтр, Card поимки, Плитка вида, Степпер, Banner, Погодная строка, Input с плавающим лейблом, TabBar, Бейджи синхронизации.
- Страница `/dev/gallery` — живой стенд всех компонентов во всех состояниях (для визуальной сверки с [zorka-ui.html](../design/zorka-ui.html) и будущих регрессий).

**Результат:** компонентная база дизайн-системы существует в коде и выглядит как макет.

**Проверка:** Vitest-тесты состояний (disabled, active, error); сверка галереи с макетами — probe-скриптом переполнений (тот же, что проверял макеты) + глазами на устройстве.

## Этап 3 · Локальный стек Supabase и схема (~3 дня)

**Задачи**
- `supabase init` + `supabase start` (полный стек: Postgres 54322, Auth, Storage, Edge, Studio).
- Миграции по [03-data-model.md](03-data-model.md): `places`, `catches` (jsonb `weather`), `catch_photos` + bucket `catch-photos` и политики, `fishing_trips`, `weather_cache`; RLS `user_id = auth.uid()` на всех пользовательских таблицах; индексы под запросы ленты и статистики.
- Сид `species` (готов: [0001_species.sql](../supabase/migrations/0001_species.sql), 51 вид, идемпотентен).
- Edge Function `get-weather` (TypeScript): OWM за кэшем-таблицей, TTL 30 мин (current) / 3 ч (forecast); ключ — в секретах, не в коде. **Нужен OWM API-ключ заказчика (бесплатный тариф).**
- Сквозной тест RLS: два тестовых пользователя не видят записи друг друга.

**Результат:** `supabase db reset` поднимает воспроизводимую схему с сидом; погода приходит через Edge Function с кэшированием.

**Проверка:** SQL-миграции инструментально (баланс скобок, идемпотентность — как проверяли сид); интеграционный тест RLS; curl к Edge Function с горячим и холодным кэшем.

## Этап 4 · Auth и каркас экранов (~4 дня)

**Задачи**
- Экраны входа/регистрации по макету 05 (RHF + zod), Zustand-стор сессии, protected routes, автологин по сохранённой сессии Supabase.
- Таб-бар + четыре экрана-каркаса (Лента, Запись, Карта, Итоги) с пустыми состояниями по макетам 01–04 и оффлайн-баннером (§6.6, §7.1).
- Первый сквозной запрос данных: справочник видов `species` из Postgres → repository → экран «Запись» (сетка плиток §6.4, поиск).

**Результат:** приложение выглядит как макеты, вход работает, справочник читается из БД через repository-слой (UI не трогает Supabase SDK — правило 02-architecture).

**Проверка:** e2e-смоук (Vitest + browser): регистрация → вход → перезагрузка → сессия жива → на экране записи 51 вид; RLS-фильтрация сид справочника (общий) vs записей (личных).

## Этап 5 · IndexedDB, outbox, PWA (~4 дня)

**Задачи**
- Dexie-схема (кэш справочников, кэш данных, outbox) + liveQuery-хуки в repositories.
- Sync engine: создание поимки оффлайн → очередь → досылка FIFO при появлении сети; состояния §6.11 в трёх местах (баннер, бейдж карточки, счётчик таб-бара).
- `vite-plugin-pwa`: manifest, иконки (нужна иконка приложения — заказчик или варианты от нас), precache ассетов, офлайн-fallback.
- Установка PWA на телефон заказчика; проверка safe-area таб-бара (вопрос №7 §10) на реальном устройстве.

**Результат:** фаза 1 закрыта — см. критерии ниже.

**Проверка:** сценарий «включить авиарежим → записать поимку → выключить → запись ушла» на устройстве; Lighthouse PWA-аудит.

## Критерии готовности фазы 1

1. `pnpm verify` зелёный (typecheck + lint + test + build).
2. Регистрация/вход/автологин работают против локального стека; RLS-тест двух пользователей проходит.
3. Справочник видов читается из БД через repositories на экране записи.
4. Оффлайн-создание записи попадает в outbox, после сети — синхронизируется; состояния видны в трёх местах.
5. PWA устанавливается на телефон, работает офлайн, safe-area не перекрывает таб-бар.
6. Компоненты галереи соответствуют макетам (probe + устройство); HEX вне tokens.css отсутствует (stylelint).

## Риски и отступления

- **Docker — зависимость dev-окружения** (ADR-0011): недоступность Docker останавливает этапы 3–4, но не UI-работу этапов 1–2, 5.
- **Supabase CLI и версионирование миграций**: фиксируем версию CLI в репозитории (`supabase/config.toml` + документированная версия), чтобы `db reset` не менял поведение между машинами.
- **Времена этапов — оценки, не обязательства**: порядок неизменен (каждый этап опирается на предыдущий), объём может сдвигаться в пределах фазы.
- **CI отложен** (решение от 2025-09-22): до появления удалённого репозитория единственная проверка — `pnpm verify` перед каждым коммитом; дисциплина фиксируется в этом документе. Обновление: CI включён после создания удалённого репозитория (2026-09-23, `ci.yml`); CD — см. спеку CD от 2026-09-23 (`deploy/README.md`, `.github/workflows/cd.yml`).

# ADR-0011: Локальный стек Supabase для разработки

- **Статус:** Принято
- **Дата:** 2025-09-22

## Контекст

ADR-0002 выбирает Supabase как BaaS. Для фазы 1 (каркас, миграции, Auth, Edge Functions) нужно окружение, где всё это реально работает и проверяется. Варианты окружения:

- облачный проект Supabase сразу;
- чистый Postgres (контейнер `postgres-local` на машине разработчика);
- локальный стек Supabase через CLI (`supabase start`), поднимающий Postgres + Auth + Storage + Edge Functions целиком.

Решающий фактор: **RLS-политики `auth.uid()`, Auth, Storage и Edge Functions существуют только внутри Supabase-обвязки.** В чистом Postgres миграцию можно применить, но ключевые механизмы безопасности и интеграции проверить невозможно — половина фазы 1 осталась бы непроверенной. Схема ещё не стабильна, гонять миграции сразу по облачному проекту рано. Docker Desktop в WSL разработчика работает (29.2.1), значит локальный стек доступен без новых внешних зависимостей.

## Решение

**Локальный стек Supabase (supabase CLI + Docker) — единственная среда разработки фаз 1–2.**

- `supabase start` поднимает полный стек: Postgres (порт 54322), Auth, Storage, Edge Functions, Studio.
- Миграции и сид `species` применяются через `supabase db reset` / `db push`; RLS и Edge Functions проверяются по-настоящему, не «на глаз».
- Облачной проект Supabase создаём позже — в фазе 3, когда понадобятся staging и доступ друзей. Миграции идемпотентны и переезжают в облако без правок.

## Альтернативы, которые рассматривали

- **Облачный проект Supabase сразу** — требует аккаунта и проекта до стабильной схемы; разработка по живому внешнему проекту медленнее и шумнее; отклонено на фазе 1.
- **Чистый Postgres (`postgres-local`) + облако позже** — RLS/Auth/Storage/Edge не проверить; две расходящиеся среды; контейнер разработчика оставлен для других задач, в проекте «Зорька» не используется.

## Последствия

### Позитивные

- Полноценное тестирование RLS, Auth, Storage и Edge Functions локально и без внешних аккаунтов.
- `supabase db reset` даёт воспроизводимую БД из миграций за секунды — сид и схема проверяются на каждом изменении.
- Переезд в облако — те же файлы миграций, нулевые правки схемы.

### Негативные / риски

- Docker Desktop становится зависимостью dev-окружения (в WSL работает; недоступность Docker = невозможность локальной разработки БД, но не UI).
- Локальные данные эфемерны (тома Docker); всё ценное обязано жить в миграциях — это уже политика проекта.

### Нейтральные

- Контейнер `postgres-local` у разработчика проекту не нужен и не используется.

# ADR-0002: Supabase как BaaS

- **Статус:** Принято
- **Дата:** 2025-09-22

## Контекст

Нужны: реляционные данные со сложными запросами (статистика по видам/местам/погоде), аутентификация, файловое хранилище для фото, серверный прокси для внешних API (погода), RLS-изоляция данных пользователей. Команда маленькая, этап 1 — «я и друзья», горизонт — публичный продукт на тысячах пользователей. Свой бэкенд требует инфраструктуры, мониторинга и времени.

## Решение

Используем **Supabase** как бэкенд: Postgres + Auth + Storage + Edge Functions. Клиент не знает о Supabase напрямую: доступ только через data-слой (repositories), доменные типы — наши, а не сгенерированные из схемы.

## Альтернативы

- **Свой Node/TS бэкенд (NestJS + Postgres)** — полный контроль, но недели работы над auth/файлами/инфраструктурой до первой бизнес-фичи.
- **Firebase/Firestore** — слабые агрегатные запросы для статистики, noSQL мешает погодной аналитике.
- **Serverless (AWS Amplify/GCloud)** — сопоставимо по скорости старта, но хуже DX локальной разработки и жестче lock-in.

## Последствия

### Позитивные
- Auth, Storage, RLS, Edge Functions из коробки; локальная разработка через Supabase CLI.
- Чистый Postgres — стандартный SQL, миграции версионируются, данные экспортируются без vendor-привязок.
- Цены масштабируются с проектом (free tier достаточно для этапа 1).

### Негативные / риски
- **Vendor lock-in.** Смягчение: repositories изолируют SDK; схема без нестандартных типов; при ростх можно поднять self-hosted Supabase или перевести data-слой на свой API.
- Edge Functions ограничены по рантайму — погодный кэш делаем в Postgres, не в функциях.
- Квоты free tier (БД, трафик Storage) — мониторим, при исчерпании платный план.

### Нейтральные
- Row Level Security становится единственным механизмом авторизации данных — обязанность думать о политиках на каждую таблицу.

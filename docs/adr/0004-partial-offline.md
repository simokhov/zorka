# ADR-0004: Частичный оффлайн с outbox

- **Статус:** Принято
- **Дата:** 2025-09-22

## Контекст

Ловля происходит вне зоны связи. Ценность продукта — «запись не теряется». При этом полный оффлайн-first (двусторонняя синхронизация с редактированием и разрешением конфликтов) — это на порядок более сложная система, чем нужно на этапе «я и друзья».

## Решение

**Частичный оффлайн:**

1. **Чтение** — из локального кэша (IndexedDB): последние поимки, места, справочники. Свежесть — «на момент последней синхронизации».
2. **Создание** — работает полностью оффлайн: запись и фото пишутся локально в **outbox** со статусом `pending`, UI показывает их как обычные.
3. **Редактирование/удаление** — только онлайн (в MVP). Оффлайн-редактирование — осознанно вырезано.
4. **Sync engine** — при появлении сети досылает outbox FIFO (поимки → фото), с повторами через экспоненциальную задержку. Сервер — источник истины: успешный ответ закрывает `pending`, ошибка — повтор.
5. Конфликты из-за UUID, генерируемых на клиенте, не возникают; коллизии по данным исключены, т.к. оффлайн меняется только создание.

## Альтернативы

- **Полный оффлайн-first (CRDT/двусторонний sync)** — лучший UX, но сложность разрешения конфликтов и тестирования непропорциональна этапу; путь миграции: после стабилизации MVP добавляем редактирование в outbox, формат уже готов.
- **Онлайн-only** — неприемлемо: приложение бесполезно в главном сценарии.
- **Только кэш-чтение без оффлайн-создания** — теряет ключевую ценность («ничего не потерять»).

## Последствия

### Позитивные
- ~80% ценности оффлайна за ~20% сложности; предсказуемая модель без конфликтов.
- Единый код-путь записи (онлайн = оффлайн + фоновая досылка), нет двух веток логики.

### Негативные / риски
- Пользователь не может поправить/удалить запись без сети — компромисс принят; UI явно показывает состояние.
- Блобы фото в IndexedDB занимают место (iOS evictable storage) — чистим очередь после подтверждения сервера, ставим storage persistence request.
- Дубли при повторной отправке возможны при обрыве после коммита — идемпотентность по клиентскому UUID (upsert по `id`).

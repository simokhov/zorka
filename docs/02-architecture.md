# Архитектура системы

## 1. Обзор

«Зорька» — PWA с тонким клиентом и BaaS-бэкендом. Вся предметная логика, доступная клиенту, живёт во фронтенде; Supabase отвечает за данные, аутентификацию и файлы; внешние API (погода, карты) изолированы за Edge Functions и абстракциями.

```
┌─────────────────────────────────────────────┐
│                 PWA (React)                 │
│  ┌─────────────────────┐  ┌─────────────┐  │
│  │   Feature-слои UI    │  │ Service     │  │
│  │  Catch / Map /      │  │ Worker      │  │
│  │  Weather / Stats    │  │ (outbox sync)│ │
│  └────────┬────────────┘  └─────────────┘  │
│           │                                  │
│  ┌────────▼───────────────────────────────┐ │
│  │ Data-слой (repositories + IndexedDB)   │ │
│  └────────┬───────────────┬───────────────┘ │
└───────────┼───────────────┼─────────────────┘
            │               │
   ┌────────▼───────┐  ┌────▼──────────────┐
   │  Supabase      │  │  Yandex Maps JS   │
   │  - Postgres    │  │  (клиентский SDK) │
   │  - Auth        │  └───────────────────┘
   │  - Storage     │
   │  - Edge Funcs ─┼──► OpenWeatherMap API
   └────────────────┘
```

## 2. Слои клиента (React + Vite + TS)

| Слой | Ответственность |
|---|---|
| **UI / features** | Экраны и компоненты по доменам: `catches`, `map`, `places`, `weather`, `stats`, `auth` |
| **Domain** | Типы предметной области (`Catch`, `Place`, `SpeciesRef`), чистая логика (валидация, агрегация статистики) |
| **Data (repositories)** | Единый API доступа к данным: сначала локальный store, при необходимости — сервер. Скрывает Supabase от UI |
| **Local store** | IndexedDB (Dexie) — кэш справочников и данных, очередь outbox для записей, созданных оффлайн |
| **Sync engine** | Service Worker + периодический опрос сети: досылка outbox, обновление кэша (ADR-0004) |

Правило: **UI никогда не вызывает Supabase SDK напрямую** — только через repositories. Это страхует от миграции с Supabase на свой бэкенд (этап 2).

## 3. Бэкенд (Supabase)

- **Postgres** — единственный источник истины. Схема — [03-data-model.md](03-data-model.md). Изоляция данных через Row Level Security по `auth.uid()`.
- **Auth** — email+пароль сейчас, OAuth-провайдеры позже (ADR-0008).
- **Storage** — фото улова: bucket `catch-photos`, оригиналы + превью, публичный доступ только через signed URL (ADR-0007).
- **Edge Functions** — единственная точка вызова OpenWeatherMap (ключ на сервере, кэш ответов в таблице `weather_cache`), возможные вебхуки и системные операции (ADR-0006).

## 4. Внешние сервисы

| Сервис | Роль | Изоляция |
|---|---|---|
| **Яндекс.Карты JS API** | Карта, геокодинг названий мест | Обёрнут в модуль `map-provider` (ADR-0005) |
| **OpenWeatherMap** | Текущая погода + прогноз 5 дней | Только через Edge Function; клиент не видит ключ и лимиты (ADR-0006) |

## 5. Ключевые сценарии

### 5.1 Запись поимки онлайн
1. UI собирает форму → repository создает `Catch` в локальном store со статусом `synced: pending`.
2. Repository пишет в Postgres, загружает фото в Storage, ставит `synced: ok`.
3. UI показывает запись немедленно (оптимистично).

### 5.2 Запись поимки оффлайн
1. То же, но шаг 2 откладывается: запись + фото остаются в IndexedDB outbox.
2. При появлении сети sync engine досылает записи (FIFO), конфликты решаем: серверная правка данных новее локальной (у сервера приоритет, т.к. редактирование оффлайн не поддерживается в MVP).

### 5.3 Погода в точке
1. Клиент вызывает Edge Function `get-weather?lat&lon&mode=current|forecast`.
2. Function проверяет кэш (таблица `weather_cache`, TTL 30 мин для current / 3 ч для forecast), иначе идёт в OWM, кладёт в кэш, возвращает клиенту.

### 5.4 Обогащение поимки погодой
- Если сеть есть — погода прикладывается при создании записи (вызов из клиента в момент сохранения, при недоступности — поле остаётся пустым и дозаполняется при первом sync, см. ADR-0006).

## 6. Безопасность

- RLS на всех пользовательских таблицах: `user_id = auth.uid()`.
- Фото: доступ по signed URL с TTL; прямые ссылки не выдаются.
- Ключи OWM и Яндекс — в env бэкенда / нужны только на сервере; ключ Яндекс.Карт, увы, публикуется в клиенте (ограничиваем доменом + HTTP-реферером в кабинете Яндекса).
- Никакого обмена данными между пользователями в MVP → RLS-политика простая и полная изоляция.

## 7. Развёртывание и среда

- **Клиент:** статический бандл (Vite), хостинг — любой CDN (MVP: Vercel/Netlify); CI собирает и деплоит из main.
- **Бэкенд:** Supabase-проект (cloud). Миграции схемы — через `supabase/migrations`, применяются CLI в CI.
- **Среды:** `local` (supabase local dev), `staging` (закрытый доступ друзей), `production` (пока идентична staging по составу).
- **Секреты:** `.env` локально, secrets в CI, ключи в Supabase Dashboard/CLI.

## 8. Риски и их смягчение

| Риск | Смягчение |
|---|---|
| Привязка к Supabase (этап 2 может захотеть свой бэкенд) | Repositories изолируют SDK; схема — чистый Postgres без нестандартных типов; миграция = замена имплементаций data-слоя |
| Лимиты/цены OpenWeatherMap | Edge-кэш погоды; абстракция `WeatherProvider` позволяет сменить провайдера одним модулем |
| Яндекс.Карты — платный лимит загрузок (MP) | Счётчик загрузок карты, ленивая загрузка тайлов, режим «список без карты»; мониторинг квоты |
| Оффлайн-конфликты данных | MVP запрещает редактирование оффлайн — только создание; конфликтная поверхность минимальна |
| Потеря фото из очереди | Фото в outbox хранится до подтверждения сервера; повторные попытки с экспоненциальной задержкой |
